Resumen ejecutivo

El sistema se divide en una capa publica de proxy y una capa productiva de negocio. La mayor parte del mantenimiento debe realizarse en `restapi_prod`; la capa `restapi_client_prod` debe mantenerse ligera y estable para clientes externos.

Las areas funcionales criticas son expediciones/Movertis, temperaturas, contabilidad, facturas impagadas y morosos.

1. Arquitectura del sistema

Modelo de capas y responsabilidades principales.

Arquitectura
Clientes externos Odoo, Postman, frontales, integraciones
→
restapi_client_prod Proxy publico, validacion, reenvio JSON
→
restapi_prod Negocio, SQL Server, MySQL, Movertis, SMTP

`restapi_client_prod`

Debe permanecer como capa de entrada estable y ligera.

  • Valida API key.
  • Valida parametros minimos.
  • Reenvia payload y `Authorization`.
  • Devuelve respuesta normalizada al consumidor.

`restapi_prod`

Concentra la logica de negocio y acceso a datos.

  • Consulta SQL Server Mtrans.
  • Accede a MySQL interna.
  • Orquesta expediciones, temperaturas y reportes.
  • Integra Movertis y SMTP.

3. Configuracion

Archivos principales y responsabilidades de configuracion.

Configuracion

Negocio: `restapi_prod/include/Config.php`

  • Conexion MySQL interna.
  • Conexion SQL Server Mtrans.
  • API key administrativa.

Proxy: `restapi_client_prod/api/include/Config.php`

  • Conexion MySQL de la capa cliente.
  • Destino de `restapi_prod` via `API_PROTOCOL`, `API_HOST`, `API_PORT`, `API_PATH`.
  • API key administrativa.
Importante: las credenciales y tokens deben migrarse a variables de entorno o gestor de secretos. No deben exponerse en documentacion, logs ni commits.

4. Autenticacion

Modelo recomendado para consumidores y mantenimiento.

Seguridad

Header recomendado

Usar siempre el header estandar para evitar diferencias entre clientes HTTP:

Authorization: <api_key>

Rutas a revisar

Algunas rutas de `morosos` en `restapi_prod/v1/index.php` no declaran middleware `authenticate`. Si estan expuestas, deben protegerse o restringirse por red.

6. Modulos funcionales

Responsabilidades y puntos sensibles por dominio.

Dominios

Movertis y expediciones

restapi_prod/modules/movertis/movertis.php

  • Consulta expediciones en SQL Server Mtrans.
  • Obtiene recogidas, almacenes, repartos y salas.
  • Integra datos de Movertis.
  • `getExpeditionsData()` puede tardar mas de 2 minutos.

Temperaturas

restapi_prod/v1/index.php

  • Orquesta `getTemperatureReport()`.
  • Resuelve expedicion y centro.
  • Valida ordenante en Ramoneda.
  • Consulta vehiculos/salas y datos externos.

Contabilidad y facturas

restapi_prod/modules/account/account.php

  • Facturas de venta y compra.
  • Movimientos contables.
  • Detalle de factura.
  • `TIva` se devuelve como codigo Mtrans; el mapeo Odoo no esta en este repo.

Morosos e impagados

restapi_prod/modules/morosos/morosos.php

  • Facturas pendientes.
  • Incidencias y gestion de cobro.
  • Envio de reportes.
  • Revisar autenticacion de rutas expuestas.

7. Flujos criticos

Secuencias operativas que conviene entender antes de modificar codigo.

Flujos

Odoo / cliente externo -> expediciones

Solicitud externa `POST /api/v1/getExpeditionsData` con API key y rango de fechas.
Proxy `restapi_client_prod` valida y reenvia el JSON a `restapi_prod`.
Negocio `restapi_prod` consulta Mtrans y compone expediciones.
Respuesta Se devuelve JSON al consumidor externo.

Reporte morosos

Solicitud `POST /morosos/send_report_morosos`.
Proxy Reenvio a endpoint productivo.
Modulo `sendReportMorosos()` genera y envia reporte.
Resultado JSON con estado del proceso.

8. Diagnostico operativo

Guia rapida ante errores frecuentes.

Operacion

Error cURL

There is an error in the cURL request

  • Origen: `CallAPI()` en `restapi_client_prod/api/include/functions.php`.
  • Revisar log `CallAPI cURL error`.
  • `28`: timeout, `7`: no conecta, `6`: DNS.
  • Probar `restapi_prod` desde el mismo servidor del proxy.

Respuestas lentas

Especialmente en `getExpeditionsData`.

  • Medir llamada directa a `restapi_prod`.
  • Comparar contra timeout configurado.
  • Revisar tamano del JSON y numero de expediciones.
  • Particionar por dia/centro cuando sea posible.

Puntos que deben considerarse en mantenimiento y evolucion.

11. Recomendaciones priorizadas

Plan de mejora recomendado para el equipo de mantenimiento.

Roadmap
  • Centralizar configuracion sensible fuera del repositorio.
  • Normalizar autenticacion en todos los endpoints, incluyendo `morosos`.
  • Separar timeouts por endpoint o permitir timeout configurable.
  • Optimizar `getExpeditionsData` para respetar filtros, paginar o reducir payload.
  • Documentar contratos JSON request/response de endpoints criticos.
  • Anadir scripts smoke o tests automatizados para despliegues.
  • Mejorar trazabilidad de errores sin exponer datos sensibles al consumidor.
